## A. Orientation — customer side and shop side look the same

**A1. The two headers are nearly identical, and both show the same shop name.**
The dashboard header (`app/dashboard/layout.tsx`) and the shop header
(`app/shop/[shop_slug]/ShopHeader.tsx`) are both: shop name top-left, small controls
top-right, same `border-b` style, white page. On both sides the top-left text is literally
the same string — the shop's name ("test"). The only difference is which small grey
controls sit on the right (`กฎของร้าน` + `ออกจากระบบ` vs `TH`/`EN`). Nothing anywhere says
"this is your management dashboard" or "this is what customers see."

*Direction:* make the dashboard visually its own place — a distinct header color or a
"แดชบอร์ดร้านค้า" label next to the shop name, or both. This is the highest-leverage single
fix for the confusion, and it dovetails with the already-wanted dashboard look-and-feel
pass (resume.md).

**A2. Every page has the same browser-tab title.**
Only the root layout sets metadata, so every page — landing, login, dashboard, fit rules,
customer shop, garment — is titled `Fit MVP — หาขนาดที่ใช่`. Open three tabs and they are
indistinguishable.

*Direction:* per-page `metadata`/`generateMetadata`: e.g. "แดชบอร์ด — Fit MVP",
"{garment name} — {shop name}", "เข้าสู่ระบบ — Fit MVP". Small, mechanical, cheap.

**A3. "Preview shop" opens a new tab with no marker that you switched sides.**
`GarmentCard` links the whole card to the public garment page in a new tab
(`target="_blank"`, tooltip `ดูหน้าร้าน`). Combined with A1 + A2 the founder ends up with
several identical-looking, identically-titled tabs, some dashboard, some customer view.
This is very likely the exact moment the "which side am I on?" feeling happens.

*Direction:* fixing A1 + A2 mostly fixes this. Optionally add a small "กำลังดูแบบลูกค้า"
(viewing as customer) banner when the visitor also has a retailer session — nice-to-have,
not required.

## B. Dead ends and missing back routes

**B1. Login and signup pages are isolated boxes.**
`/login` has: heading, email, password, submit. No link to signup, no link back to the
landing page, no forgot-password. `/signup` likewise has no link to login. A retailer who
picks the wrong page has only the browser back button. (This is the literal "no back
button" complaint.)

*Direction:* one line under each form — "ยังไม่มีบัญชี? สมัครสมาชิก" / "มีบัญชีแล้ว?
เข้าสู่ระบบ" — and make the page heading or a small logo link to `/`.

**B2. 404s are the default Next.js page: English-only, unbranded, no way out.**
A mistyped shop link (LINE truncates URLs; customers retype them) lands on a bare white
"404 This page could not be found" with zero links, in English, for a Thai customer.
Same for a deleted garment's old link. There is no custom `not-found.tsx` anywhere.

*Direction:* add `app/not-found.tsx` (Thai + EN, link to `/`) and a shop-level
`not-found.tsx` that says "ไม่พบสินค้านี้" and links back to the shop page.

**B3. On dashboard subpages, the only way back is a link that doesn't look like one.**
On `/dashboard/fit-rules` and the garment forms, the route back to the dashboard is
clicking the shop name in the header — plain text styling, nothing signals it's clickable.
The garment form at least has a `ยกเลิก` link; the fit-rules page has nothing page-level.

*Direction:* a visible "← กลับไปแดชบอร์ด" link at the top of each subpage (the shop side
already does exactly this on the garment page and it works well), or breadcrumbs.

**B4. The shop header's shop name is not clickable.**
On the customer garment page the header shows the shop name as a plain `<span>`. Customers
(and the founder) instinctively click the name to go "home" to the shop — nothing happens.
The only route back is the smaller `← กลับไปหน้าร้าน` text link.

*Direction:* make the shop name a link to `/shop/[slug]`. One-line change; also makes the
two headers behave consistently (the dashboard name *is* a link).

**B5. Visiting `/dashboard` logged-out silently dumps you on `/login`.**
No message explains why you're suddenly on the login page. With A1/A2 in play, an
expired-session redirect looks like the app randomly changed screens.

*Direction:* low priority; a small "กรุณาเข้าสู่ระบบก่อน" notice (e.g. via a query param)
would do.

**B6. The landing page has no path for customers.**
`/` speaks only to retailers (login/signup). A curious customer who trims the URL down to
the domain root gets nowhere — no explanation that shops have their own links, no example.
Acceptable for MVP; worth one sentence of copy ("ลูกค้า? เปิดลิงก์ร้านที่ได้รับจากร้านค้า").

## C. Comprehension — the app is understood to be working, but says confusing things

**C1. Fit results show a "+" number for "too tight."**
Live result observed: `คับเกินไป (+46.0cm)` — chest. The sign shown is
customer-minus-garment, so *positive means too small*. Everywhere else in the product
(fit-rules, the ease model) the convention is garment-minus-customer, where positive means
roomy. A customer reads "too tight, plus 46 cm" and has to guess what the number means; a
retailer who knows the ease convention will read it as *backwards*.

*Direction:* drop the raw signed number in favor of words: "คับไป 46 ซม." / "หลวมไป 3 ซม."
(too tight by / too loose by, always positive), or flip the sign to match the ease
convention used everywhere else. Display-only change in `FitChecker.tsx`.

**C2. The fit-rules page is effectively unreachable. (known — decision pending)**
Still the top navigation defect on the shop side: the only entry is small grey header text
beside Logout. Options were mocked up 2026-08-13; founder deferred the choice. Should be
decided together with A1/B3 since all three touch the dashboard header/nav.

**C3. A database failure on the fit-rules page reads as "no rules yet." (known)**
`app/dashboard/fit-rules/page.tsx:13` discards the query error, so a real failure renders
`ยังไม่มีกฎของร้าน`. Fix regardless of navigation decisions.

**C4. Every login failure shows the same generic message.**
Wrong password, no such account, rate-limited — all collapse to
`เกิดข้อผิดพลาด กรุณาลองใหม่` by design (to avoid surfacing Supabase's English). The
retailer can't tell whether to retype the password or sign up.

*Direction:* map the two common Supabase auth errors (invalid credentials / user exists)
to specific Thai messages; keep the generic one as fallback.

**C5. Returning customers get silently pre-filled measurements.**
Confirmed live: reload the garment page and the previous numbers reappear (via
`/api/fit/last`). Good feature, zero explanation — a customer may not remember entering
them, and on a shared device they are someone else's numbers.

*Direction:* one line above the form when values were pre-filled: "ใช้ขนาดล่าสุดของคุณ"
with a clear-all affordance. Low priority.

**C6. Dashboard is Thai-only / no toggle. (known — founder raised 2026-08-13)**
Unchanged. Login, signup, and landing are also toggle-less (landing shows static EN
subtext). Listed for completeness; the wiring plan is already in resume.md.

## D. Minor polish

- **D1.** Garment delete uses `window.confirm` and errors via `alert()` — native browser
  dialogs, inconsistent with the inline red-text errors everywhere else. Fine for MVP.
- **D2.** `ยกเลิก` (cancel) on the garment form and fit-rules editor discards typed work
  with no confirmation. The only unsaved-work guard in the app is the category-change one.
- **D3.** Ticking "ปรับเฉพาะสินค้านี้" seeds the custom rule editor from the default rule,
  not from the rule currently in force. (known follow-up in resume.md)
- **D4.** The fit-rules list summary misreads for negative ease ("กว้างกว่าตัว -4–3 ซม.").
  (known follow-up in resume.md)
- **D5.** Garment-form validation shows one error at a time in a single block above the
  submit button (first failing check wins) — acceptable, but on a long form the message can
  be far from the offending field.
- **D6.** `(cm)` suffix is hardcoded Latin text in both languages. Harmless; noting so
  nobody "fixes" it into scope accidentally.
- **D7.** Unfilled dimensions render as `ไม่ได้ระบุ` rows in results — informative but
  noisy when a customer fills only one field of five.
